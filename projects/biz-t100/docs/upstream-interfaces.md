## 2. 四个接口的职责

公共报文为 POST、`type=sync`、host 元数据、`service.prod=T100`、服务名、`datakey.EntId` 和 `payload.std_data.parameter`。企业、地址与凭据由受控运行配置决定；参数中的 enterprise_no 如提供必须与配置一致。服务 key 仅在调用者许可通过后读取。

| 服务 | 对象与主要输入 | 输出与闭环 |
|---|---|---|
| `employee.data.create` | 新员工档案；employee[] 中员工号、全名、部门、status 必填，另支持姓名分段、职务、联系信息、备注等文档字段 | 总执行码、逐条 source_no/erp_no/execute_description；再精确回读提交字段 |
| `employee.list.data.query.get` | 工号/姓名、部门、日期、分页、data_time/key_condition、conditions/orders | 员工数组与分页信息；维护检索允许零条或多条候选 |
| `employee.data.update` | 已有员工档案；employee_no 加至少一项修改，status Y/N 也是档案字段 | 前查存在且唯一、保留原资料、逐条更新回执、修改及保留字段回读 |
| `user.account.create` | 已有员工对应的登录账号；master[] 含账号、工号、账号状态 gzxastus、复制/重置开关及权限明细 | 承载账号启停、密码重置等操作；成功回执不直接证明账号状态、密码或权限已生效 |

员工档案是资料更新和账号维护的前提。新建档案不隐式创建登录账号；查询没有匹配不自动建档。维护检索的候选列表不会自动选择第一人执行写入。本人服务以及写入前查/回读仍要求恰好一条、工号全等、没有下一页；企业和工号共同标识对象，姓名只作检索或展示。

员工号与登录账号分别指定，查询 account_no 不用于推定登录账号；其为空也不能推出“未绑定”。四接口维护使用显式操作员许可，与原本人映射授权分开。业务参数确定操作目标，不能替代原生验签得到的调用者身份。

四接口当前在同一个 FastMCP `maintenance` 实例中实现，不按接口拆服务；是否向某客户端开放，取决于部署动作、签名 scope、服务端许可及 GOV 白名单。产品查询模型支持姓名等检索；当前常驻查询主体仅获批工号精确查询，不能由模型支持反推已获广泛检索许可。实际连接范围见 [工具契约](tool-contracts.md)。

## 3. 员工档案更新与保留原资料

用户已明确区分：员工接口的status是档案状态，登录账号启停使用用户接口的gzxastus。员工查询不能验证登录账号状态或密码；此前把员工status当作账号启停的理解已订正。此前“省略员工字段会保留”的确认保留为来源；用户本次提供并确认可完整执行的脚本，则在更新前查询、回填原资料，脚本注释记录全量覆盖会清空省略字段。当前实现据[RU-006](../../../docs/reuse/RU-006-T100已验证脚本与测试许可修正.md)主动保留原值，不再依赖服务器的省略行为。

FastMCP的employee_update输入是修改意图，例如：

```json
{"employee": [{"employee_no": "E001", "status": "N"}]}
```

这不是直接发往T100的最终报文。服务先按受控企业与工号精确查询唯一员工，在白名单内补回未修改字段，再覆盖用户明确提交的字段。白名单为full_name、department_no、status、last_name、middle_name、name、job_title、bank_account、account_no、email、telephone、mobile_phone；需要保留的值查询未提供时拒绝写入，不猜测为空。显式空字符串表示清空，与省略不同。前查中已知为空、且用户未要求修改的可选字段按参考实现从实际报文省略，仍纳入回读核对；不能将缺失或null臆造为空。姓名分段与联系方式会随员工status更新保留。

原始意图用于授权与审计；最终报文重新校验目标、字段和摘要，写前保存effective-request.json。补回值只能来自同一员工本次前查，不能加上另一员工资料或把服务凭据当作业务字段。写后回读同时验证修改及保留字段。没有上游版本条件时不能保证与其他客户端并发修改的原子性。

remark、modify_no及日期不自动回填。参考脚本注释称remark曾不落库，因此备注修改只作兼容性诊断，不能承诺是当前环境已跑通的资料修改用例。创建日/修改日精确往返未验证，提交时仍列unverified_fields；明确提交的其他可查询字段继续核对。账号层gzxastus负责登录账号启停；角色/据点状态与员工status也是独立字段。

## 4. 用户账号维护的多种操作

| 字段 | 文档与本地契约 |
|---|---|
| gzxa001 | 登录用户编号，独立显式填写；即使某测试用户与工号相同，也不设全局默认 |
| gzxa003 | 员工工号，必须已有员工档案 |
| gzxastus | 登录账号状态；Y启用、N禁用，显式指定，不默认启用；CLI为--account-status |
| password_reset | 是否重置 Y/N，显式指定；不是新密码字段 |
| is_reproduce | 是否复制 Y/N，显式指定 |
| reproduce_acct | 文档定义为被复制工号；仅在复制 Y 时提供，真实测试必须另行批准该员工来源，不能用账号编号替代工号授权 |
| detail[] | 角色/作业层：gzxbstus、类别 gzxb002、编号 gzxb003、有效日期 gzxb004/005 |
| detail[].detail1[] | 据点层：gzxcstus、据点 gzxc004、有效日期 gzxc005/006、允许下发 gzxc007 |

新增/修改登录账号、账号禁用/启用、密码重置、复制和权限明细共用 user.account.create，由提交参数决定组合，不拆成多套计划脚本。文档没有独立 update-only 标记或密码值参数，不推定不存在账号必定被拒绝、默认密码、复制覆盖规则或权限合并规则。用户确认省略 detail 会保留既有角色/站点；此确认不等于空数组或部分明细一定保留。

### 当前内部网关限定的账号动作

MetaMCP 账号 endpoint 只暴露同一个 `t100_account_maintain`，由 BIZ 的 `account_profile=status-password` 限定五字段最小请求，不改变上游完整接口定义。

| 动作 | gzxastus | is_reproduce | password_reset | 当前效果证据 |
|---|---|---|---|---|
| 禁用登录账号 | N | N | N | 成功回执；实际状态需账号资料或登录核验 |
| 启用登录账号 | Y | N | N | 同上 |
| 启用状态下重置密码 | Y | N | Y | 成功回执；实际密码需登录核验 |

另外两个字段为 `gzxa003`（工号）和 `gzxa001`（账号），必须匹配批准配对范围。该 profile 不接受复制、`reproduce_acct`、`detail`（包括空数组）、其它字段或禁用同时重置。当前批准范围只支持单条目标。本机完整 `full` profile 仍保留批量、复制及权限明细能力，须各自独立许可。账号状态 Y 与重置 Y 是两个同时提交的操作，不能把重置解释为自动保留原账号状态。接口不会返回新密码；默认密码及交付流程仍由维护方说明。

## 5. 文档差异与本地约束

- is_reproduce 在表格及 JSON 样例有不同尾随空格，条件描述及既有实现使用无空格键；本项目固定无空格键。
- 查询参数表把 employee_no、date_s/date_e 标为必填，又注明 parameter 可只传部分参数。已取得不带日期的真实工号查询证据；仅姓名查询虽有离线模型和报文支持，当前服务器兼容性仍需真实验收。
- 查询样例出现与参数定义不符的服务名，固定使用 employee.list.data.query.get。多份 JSON 样例缺少闭合符或含说明性占位，不直接复制执行。
- is_digiwin_product 允许 Y/N，默认 N 是本实现明确选择，不能把示例 Y 或企业、地址、key 当作当前配置。
- 当前旧 test 入口据用户确认与生产数据一致；名称不代表数据隔离，不擅自切换企业或地址。
- 本地请求要求明确业务筛选条件，日期范围成对、日期真实有效；conditions 的字段/操作符/值完整。单批员工/账号100、各层明细100、请求/响应2MB、整个业务流程10秒是适配器限制，不是声称 T100 的数据库或服务器上限。

## 6. 回执、错误和证据

execution.code 文档定义为字符串，0 成功；实现仅兼容字符串 "0" 或整数 0，不接受布尔或浮点伪成功。员工写入必须覆盖每个目标且没有重复，source_no/erp_no 与提交工号全等；执行描述为空字符串或纯空白时表示成功。此前真实回执使用一个空格，此兼容已实现，仅规范化描述，绝不裁剪或模糊匹配编号；私有原始回执保留空白原值。任一行失败不宣称整批成功或其余行回滚。

维护查询返回空列表或候选列表是合法结果。写入前查和回读空结果为 employee_not_found，多条为 employee_not_unique，错工号为 upstream_employee_mismatch，字段回读不符为 upstream_verification_failed，异常结构才为 upstream_contract_error。未知业务码仅保留安全的 HTTP/业务码诊断，不臆测其含义，不输出原始自由文本或服务 key。

员工写入的 verified 证明本次修改及应保留字段在查询时点一致。账号 acknowledged 不证明登录账号启停、密码生效、角色/据点授权、复制内容或密码交付；须通过对应账号资料或登录行为核验，员工查询不能代替。全部目标的完整逐条回执均明确失败（唯一匹配source_no、空erp_no、有失败描述）时记录failed，不产生未知占用；混合结果、超时或无法确认结果才保留unknown。失败不自动重试；新入口只读检查旧写库的未决记录，不能通过更换入口解除占用。
