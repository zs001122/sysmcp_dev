# 可信个人身份与本人映射设计

日期：2026-09-29。状态：设计基线。本文固定身份契约、拓扑要求和验收矩阵；真实签发者来源与 MetaMCP 身份传递能力属未验证外部事实，文中列为待实测项，不预断结论。本文不声明任何真实联调已通过。

## 1. 目的与范围

BIZ-T100 的身份链已在组件级实现并用合成签名身份完成离线验证（194 项），但三个问题此前只有待办条款、没有统一设计：

1. 可信个人身份由谁签发、以什么契约到达 BIZ；
2. 经 MetaMCP 两跳后身份如何保持可信与可归因；
3. 本人映射（`issuer+subject → 工号`）由谁批准、如何变更与撤销。

不提前固定这三点，后续 `biz-*` 项目会各自发明身份口径，测试结论互相不可比，真实闭环无法验收。本文是所有 BIZ 项目的身份契约基线；各系统只声明自己的执行模式与映射清单，不重新定义身份语义。

明确不做：不建 IAM 平台、用户目录或新的身份平台；本文不选定具体 IdP 产品（外部依赖，见 §4）；不把员工映射、允许清单放入 GOV；不为未来系统预建实现。

## 2. 身份要素与已有实现锚点

| 要素 | 含义 | 现有实现锚点（biz-t100） |
|---|---|---|
| 认证（谁） | 可信发行者签名 token 的 `iss` + `sub` | `IdentityProfile.issuer`、`current_caller()` |
| 归因（从哪来） | 原客户端 `azp`/`client_id` | `Caller.client_id`、`IdentityProfile.allowed_clients` |
| 受众（给谁用） | 资源受众 `aud` 与 scope | `IdentityProfile.audience`、`SCOPE = t100:employee:read:self` |
| 授权（能做什么） | BIZ 策略判定主体/客户端/工具/启停 | `ServiceAccountPolicy`、`FileServiceAccountAccess` |
| 本人映射（对应谁） | `(issuer, subject)` 唯一映射到本人员工号 | `ServicePrincipal.employee_id` |
| 执行身份（用什么执行） | 授权通过后才读取的服务 key | `EmployeeGrant.credential`（ADR-003 service-account） |

不变量（已被现有实现和测试覆盖，本文将其提升为跨项目契约）：

- 员工号只可来自受控 `issuer+subject` 映射；普通 Header、姓名、邮箱、MetaMCP API Key、工具参数、已签名但未选为权威来源的 claim 均不能指定或覆盖员工号。
- 同一 `(issuer, subject)` 只允许一条映射；多条即配置无效。
- 未映射、停用、未许可一律前置拒绝：零上游请求、零 key 内容读取。
- 映射文件原子替换即生效；在途查询按 ADR-003 的前置/后置重验规则处理，不伪报。

## 3. 拓扑：直连与两跳的身份等价要求

```text
路径 A（直连）  MCP 客户端 ──员工 token──▶ BIZ(/mcp)：AuthProvider 验签 → Caller
路径 B（两跳）  MCP 客户端 ──▶ MetaMCP endpoint(X-API-Key 入口) ──?──▶ BIZ(/mcp)
```

- 路径 A 是身份验收基线：员工 token 直达 BIZ，`current_caller()` 语义完整。
- 路径 B 中 MetaMCP API Key 只是入口访问凭据，不是员工身份（已在 GOV 准入中固定）。**两跳通过的必要条件：BIZ 在两条路径下解析出的 `Caller` 语义一致**，即同一员工在两跳下得到与直连相同的 `issuer/subject/client_id` 判定结果；否则两跳身份项不通过，不得以"网关已认证"替代。

### 3.1 MetaMCP 2.4.22 待实测能力清单

以下问题必须在现有实例上实测并记录到 [GOV 部署记录](../projects/gov/部署记录.md)，实测前不得宣称任一方案可用：

| 编号 | 待验证问题 | 验证方式 |
|---|---|---|
| Q1 | endpoint 入站 `Authorization` 是否可透传到下游已登记服务 | 两跳下探针：BIZ 侧记录实际收到的头 |
| Q2 | `enable_oauth=true` 的 endpoint 是否把用户 OAuth 身份向下游传递，还是仅作网关侧登录 | 固定版本实测 + 对照上游中间件源码 |
| Q3 | 下游服务登记时的认证头是否仅支持静态配置（静态头不能承载个人身份） | 登记配置项核对 |
| Q4 | 若 Q1–Q3 均不支持，缺口具体是什么 | 按 GOV README"先列具体接口缺口"记录 |

### 3.2 备选路径（按优先级，实测后择一）

1. **透传成立**（Q1 或 Q2 为真）：员工 token 经网关直达 BIZ，两跳与直连身份等价，按 §6 矩阵对照验收。
2. **透传不成立**：网关只承担入口访问控制与工具治理；身份验收先以路径 A 直连完成真实闭环，两跳身份项保持未通过并记录缺口；再评估上游版本能力或受控补充通道，不为此自建身份代理层。
3. 任何情况下禁止：把 MetaMCP API Key 当员工身份；工具参数传递身份；用共享静态 token 代表个人；由网关伪造无签名信任链的身份头。

## 4. 可信发行者与 token 契约

token 契约已由 `current_caller()` 固定：校验 `iss`、`aud`、`sub`、`azp`、`exp` 与 scope，签名与撤销语义归 `AuthProvider`。本文只补充签发者分级：

| 级别 | 用途 | 约束 |
|---|---|---|
| 测试签发者 | 离线开发与 `biz-validated` | 密钥不出测试；`issuer` 值必须与任何真实签发者不同，防止测试 token 在正式策略下意外有效；不进入产品 wheel 或真实装配 |
| 模拟签发者（临时，用户已确认 2026-09-29） | 真实 IdP 到位前的受控运行装配、直连与两跳链路验证 | 走完整 AuthProvider 验签路径；证据级别低于真实签发者，规则与替换路径见 §4.1 |
| 真实签发者 | `business-validated` 与发布 | 企业 IdP 或受控签发服务，属外部依赖；未确定前正式策略文件不得出现真实主体；其撤销边界（token 有效期、撤销列表）单独记录 |

### 4.1 临时模拟签发者（用户已确认，2026-09-29）

用户已确认：真实身份来源到位前，**身份主体以受控模拟签发者临时替代**。该模拟签发者是"选定但信任根为模拟"的 AuthProvider，介于测试签发者与真实签发者之间：可进入受控运行装配，证据级别不等于真实身份。规则：

1. `issuer` 值显式标记模拟性质，与任何现有及未来真实签发者不同；签名密钥独立生成、受控保存、可随时销毁轮换。
2. 仍经 AuthProvider 完整验签（`iss`/`aud`/`sub`/`azp`/`exp`/scope），禁止退化为普通 Header、姓名、工具参数、共享静态 token 或 MetaMCP API Key。
3. 模拟主体命名带显式标记，映射到授权责任人从已确认名单中圈定的两名获准用户档案号；映射文件属受控配置，不人库。
4. 证据口径：模拟身份下的直连/两跳结果记为"模拟身份链路验证"。它证明 BIZ 授权/映射/审计链路与网关传递机制，**不证明真实个人身份可信**；`business-validated` 的真实身份项保持未通过。GOV 两跳可借此完成 Q1–Q4 机制实测与 `Caller` 等价对照，身份可信性结论保留。
5. 替换路径：真实签发者到位后只改配置（issuer、密钥/验钥材料、受众、策略主体），不改代码；模拟条目与密钥同时下线，并验证模拟 token 在正式配置下被拒绝。
6. 模拟签发者只服务既定只读范围，不得用于真实写操作，不得作为真实身份失效时的回退。

本决定修订 [ADR-005](架构决策-005-T100测试接入与运行准备.md) §3"没有选定、验证真实 AuthProvider 时不生成携带测试身份的运行入口"的前提：用户已选定模拟签发者作为临时提供方，运行入口可按本节装配，证据级别按第 4 条记录。

真实签发者来源是当前最大的外部未知项，需要在 T100 接口定标同期向身份/基础设施责任方确认：是否存在可签发资源受众 token 的企业 IdP、支持的客户端类型、`azp` 归因是否可用，以及 token 能否携带档案号属性（如 employeeID）或提供 `sub` 与档案号的权威绑定来源。该确认不阻塞离线验收，但阻塞 `business-validated`。

BIZ 侧撤销已有两层保证：token `exp` 短时效；每次 `authorize()` 重读策略文件，停用/撤权原子生效。IdP 侧撤销（如用户离职但 token 未过期）由"策略文件停用该主体"兜底，生效边界为下一次 `authorize()`。

### 4.2 本轮全合成内部闭环（用户已确认）

用户进一步明确要求先在BIZ-T100内部补齐常驻启动、临时身份签发及模拟映射/凭据/上游。该独立开发装配已实现，见 [ADR-007](架构决策-007-T100内部测试服务.md) 与 [内部操作说明](../projects/biz-t100/docs/internal-test.md)。本地CLI生成并保管测试签名材料，服务端仍经原生AuthProvider验签；固定合成主体、员工和账号通过受控映射对应，不提供任意员工号参数或真实目标切换。

当前两个loopback服务分别提供本人查询和模拟重置，后者仅调用MockTransport并记录本地审计，不触及真实账号。因此不改变§4.1对模拟身份不得执行真实写入的约束。环境标记internal-simulated，真实个人身份与business-validated继续未通过；未来外部实现通过公开身份/业务端口另行装配，停用内部签发材料，保留业务授权用例。

### 4.3 获准真实员工资料的独立模拟用例

用户随后指定单名真实员工用于当前内部测试。按 [私有员工用例](../projects/biz-t100/docs/approved-employee-case.md) 将批准的工号与展示名只保存于独立私有运行配置，由带模拟标记的固定主体映射取得目标；不修改§4.2的A/B全合成基线，不把个人资料放入源码、自动测试或制品。独立签发密钥与受众隔离，只提供只读工具，强制MockTransport；工号不推定为登录账号。该用例证明目标传递一致，仍不证明真实身份或真实T100档案，不开放真实写操作。

### 4.4 真实测试业务上游（用户最新确认）

用户明确不再模拟业务系统，个人身份及登录绑定可暂存为受控测试配置。现已切换到 [真实只读宿主](../projects/biz-t100/docs/live-read.md)，实际查询指定员工，结果来自真实T100；§4.2/4.3的模拟监听已停止并保留历史证据。只读查询不需要登录账号绑定，因此该项不阻塞真实调用。临时身份仍完整验签，工号仍来自批准映射。错误服务key仍返回档案的实测缺口独立记录，不能用本轮查询成功签收真实身份、上游认证或business-validated。

### 4.5 本机命令指定工号测试（用户已授权）

用户为验证其他工号明确要求命令输入。`live_read.py call --employee-no`将本机操作者输入转为该次独立受控映射；独立临时subject、策略与审计防止并发串号，不改共享默认映射，不接受外部MCP工具employee_no参数。原生验签、读取key前授权、唯一目标校验与审计继续执行；临时签名仅在内存生成token，上游实际调用现有T100入口。此模式使用本地ASGI HTTP，默认call仍测试8768监听端口，两者证据不混同。用户同时确认旧test与生产数据一致，不再用环境名称推断空结果原因。

## 5. 本人映射生命周期

映射载体为 BIZ 持有的 `ServiceAccountPolicy.principals`（GOV 不保存，见 ADR-003/ADR-004）。

### 5.1 映射目标标识（用户已确认，2026-09-29）

用户已确认：**员工档案号即 T100 工号，是用户唯一标识**，映射目标 `employee_id` 使用档案号。由此固定以下口径：

- 档案号按字符串处理，保留前导零（如 `00000005`），禁止数值化、去前导零或位数补齐；现有 `Identifier` 模式与上游 `employee_no` 精确匹配已兼容。
- 号段规律（年份前缀、特殊 55x/56x/57x 号段、跳号）只是观察事实，不得编码为校验规则；合法性只能来自受控映射和上游精确匹配，不做本地推断。
- 名单存在重名（如两个"张玲"、两个"张丽"），再次确认姓名仅用于展示，不参与身份、授权或目标选择（BIZ-ADP 规范 §4）。
- 真实名单属员工数据，**不进入仓库、文档、示例配置或测试**；离线测试继续使用合成工号。名单本体由授权责任人保管，验收圈定的两名获准用户映射通过受控配置交付，不重复收集。
- 名单只含档案号＋姓名，不含身份主体；`(issuer, subject) → 档案号` 的绑定依据仍待真实签发者确认（§4），不得以姓名人工猜测完成绑定。

生命周期要求：

| 环节 | 要求 |
|---|---|
| 批准 | 授权责任人确认允许主体、映射依据（IdP `sub` 与档案号的对应依据）、允许客户端与工具；代码中存在映射不等于已批准 |
| 新增/变更 | 原子替换策略文件，`revision` 递增；`binding_version`（内容 SHA-256）供在途查询检测改绑 |
| 停用/撤销 | 置 `enabled=false` 或删除条目；下一次 `authorize()` 即生效；前置拒绝须为零请求零读 key |
| 变更审计 | 映射变更本身须有记录：谁、何时、依据、revision；该记录与查询审计（journal 的 caller+employee_id+request_id）分开保存、可互相对照 |
| 查询审计 | 不含凭据与完整档案；可定位每次调用的主体、映射目标、阶段与结果 |

## 6. biz-* 身份验收矩阵（闭环判定）

所有 BIZ 项目按本矩阵验收身份维度；T100 的离线部分已有对应测试（见 [离线身份链验收矩阵](../projects/biz-t100/docs/offline-acceptance.md)），真实部分待真实签发者与两跳实测。

| 场景 | 直连要求 | 两跳追加要求 | 通过证据 |
|---|---|---|---|
| 两员工本人隔离 | A、B 各持本人 token，返回严格对应各自映射工号 | 两跳下结果与直连一致 | 上游捕获的实际请求工号 |
| 伪造/过期/错受众/错 issuer | `unauthenticated`，零业务请求 | 网关不得放行无身份请求到 BIZ | BIZ 拒绝日志 + 上游零请求 |
| 未映射/停用/未许可 | 固定错误码，零请求零读 key | 同左 | 审计 + key 读取计数 |
| 客户端归因 | `azp` 不在允许清单即拒绝 | 两跳下归因不丢失、不伪造 | Caller 记录对照 |
| 撤权与改绑 | 前置重验失败零请求；后置重验失败不返回成功 | 同左，含在途调用 | 审计阶段记录 |
| 身份等价 | — | 两跳 `Caller` 与直连 `Caller` 语义一致（§3） | 直连/两跳对照记录 |

任一场景失败即身份维度未通过；网关入口认证成功、组件测试通过、上游服务级拒绝中的任何一项都不能替代其余项。
