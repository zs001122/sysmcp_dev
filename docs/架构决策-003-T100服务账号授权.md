# ADR-003：T100 服务账号授权与本人查询边界

日期：2026-09-29。状态：用户已明确授权模型；本文确定接口与验收目标，不声明新实现或真实联调通过。

## 1. 已知事实与决定

用户已说明：T100 通过开发人员维护的现有接口服务接入，调用该服务默认等同服务级管理员。因此本项目将 T100 接入模式明确为 **`service-account`**：由 BIZ-T100 在服务侧使用该接口服务的管理员 key。key 的权限类型已经明确，不再把它列为未知，也不继续要求每位员工取得 T100 用户凭据 C 或 OBO 委托凭据。

首个业务能力仍为 [ADR-002](架构决策-002-首个T100服务与扩展.md) 中的无参数只读工具 `get_my_t100_employee_record()`，返回类型化员工档案。服务账号具有较大能力，并不表示每个 MCP 用户获得管理员权限；本次仅允许受控配置中获准的用户查询本人档案。其他员工查询、批量导出及写操作均不因此开放。

现有 T100 接口服务是已存在的外部依赖，由其维护人员负责；本项目只实现调用它的 BIZ-T100，不新建一层接口代理。

```text
MCP 客户端
  → MetaMCP：入口访问控制、服务聚合与工具启停
  → biz-t100：可信用户身份、工具授权、本人范围、查询审计
  → 现有 T100 接口服务：服务管理员 key、接口能力与服务级拒绝
  → T100：按该服务账号的实际权限执行
```

## 2. 分层权限与维护责任

| 层次 | 责任与边界 |
|---|---|
| MCP 身份认证 | 认证提供方验证调用者身份、有效期与本资源受众；跨网关的员工身份及原客户端来源必须有可信依据。不能把任意 Header、工具参数或一个网关 API Key 当成员工身份证明。 |
| GOV / MetaMCP 治理 | 统一登记服务、环境地址引用、endpoint、namespace和工具暴露；入口获准不代表获准查询任何员工，也不授予 T100 管理员权限。 |
| BIZ-T100 用户授权 | 依据受控允许配置判断“哪个可信用户可调用哪个工具、对应哪个本人员工号、是否仍有效”。默认拒绝；有效映射本身不自动等于业务授权。 |
| T100 接口服务 | 验证服务 key，执行其允许的服务能力与业务规则。这里的服务级认证/授权不等于按原员工 T100 账号逐项授权。 |
| T100 | 保留对该服务账号及接口操作的实际限制；BIZ-T100 进一步限制暴露范围，不能宣称已自动继承每位员工原有的 T100 细粒度权限。 |

业务授权责任人确认允许使用本人查询的人员、映射依据及停用规则；开发人员负责实现并维护受控配置与校验。两者的责任不能由“代码中有工号映射”替代。当前尚需真实授权清单、批准来源和维护责任资料；本文没有预置允许所有用户的名单。

现有接口服务的维护人员负责提供并维护接口路径、服务名、请求/响应规范、错误码、只读副作用说明、版本兼容规则及 key 的发放、轮换和撤销方式。BIZ-T100 维护人员负责适配契约、凭据装配、授权配置与审计；外部接口变化按 [RU-001](reuse/RU-001-t100本人档案.md) 重评受影响部分。

T100服务key、员工映射、允许清单、访问策略及业务审计只由BIZ-T100持有。GOV只保存服务逻辑ID、制品版本、环境地址引用、协议、工具暴露和组合状态，不能复制这些业务敏感配置。两者通过去敏服务发布描述衔接，见 [ADR-004](架构决策-004-GOV统一服务注册与发布.md)。

## 3. `EmployeeAccess` 的服务账号实现目标

保留显式注入的 `AuthProvider`、`EmployeeAccess`、`EmployeeReader` 和 `QueryJournal`，不把业务规则放入 CORE。`EmployeeAccess.authorize(Caller) → EmployeeGrant` 的服务账号实现须满足：

1. 从已验证的调用上下文取得主体，以可信发行者和主体标识定位受控授权；核对获准客户端、工具、本人员工号、启用状态及绑定版本。授权配置的实际格式由 BIZ-T100 定义，不能由用户工具参数修改。
2. 仅在用户授权成立后为此次精确查询提供服务侧凭据。服务管理员 key 是本模式的显式依赖，不是用户凭据缺失时的自动回退。
3. 在耐久开始记录之后、查询返回之后重验授权与绑定，识别停用、撤权和改绑。调用前重验失败不得发送业务请求；调用后重验失败不得返回成功，并保留已经调用的事实。
4. 凭据仅由服务侧安全配置/凭据提供方注入，不进入工具输入、返回值、源码、示例值、审计或聊天；不把 MCP 入口 Token 直接透传为 T100 key。轮换方式和生效边界需单独验证。

工具继续拒绝工号、凭据、身份、任意 URL 等参数。客户端仅向已批准的接口发送受控本人 `employee_no` 查询，并验证返回记录唯一且目标一致，输出白名单字段；不查询全量员工后在本地过滤。具体工具输入输出与错误契约见 [T100 工具契约](../projects/biz-t100/docs/tool-contracts.md)。

上述内容是新增服务账号授权实现及测试的目标。仅阅读本文、存在接口签名或已有离线测试，都不表示真实授权配置、凭据装配与跨网关身份已接入。

## 4. 对已有假设的修订范围

本决策修订 [ADR-001](架构决策-001.md)、[ADR-002](架构决策-002-首个T100服务与扩展.md)、[RU-001](reuse/RU-001-t100本人档案.md) 与 [BIZ-ADP 规范](BIZ-ADP开发规范.md) 中涉及 **T100 必须使用员工用户 C/OBO、不得采用服务账号模式、必须比较两个员工凭据下原 API 权限差异** 的先前假设。T100 改按本文的服务账号分层授权验收，不将已澄清的权限模型继续当作阻塞。

原目标中的受控访问、权限边界与可追踪仍需实现，但证明内容必须准确：此模式证明“服务账号权限内、BIZ 明确授权的本人查询闭环”，不能据此宣称“员工原 T100 细粒度权限自动继承”。若今后要求与每位员工在 T100 内的权限逐项等价，须另取得可执行的权限来源或原接口支持，再追加实现和验证。

来源摘要、历史测试及旧报告保持原有证据范围；不修改为真实通过。原有报文、响应校验、独立项目与制品边界保持适用，新增授权实现的实际结果另记入 [T100 验证记录](../projects/biz-t100/VALIDATION.md)。

## 5. 接入仍需的实际资料

- **受控授权配置**：授权责任人确认的允许主体、员工号映射、允许客户端/工具、启用状态、更新与撤销责任；如已有有效资料只复核并引用。
- **身份承载契约**：MCP 直连与 MetaMCP 转发后的可信员工身份、原客户端归因、认证有效性和撤销方式。网关 API Key 本身不足以填补此项。
- **外部接口定标**：获准测试环境、固定目标和必要报文字段、员工查询及服务 key 失效等错误码、只读性质、接口维护责任人。真实 key 通过服务侧受控方式交付，不在文档中收集。
- **验收对象**：两名获准且映射不同员工号的用户，以及未获准、停用、改绑等场景的测试安排。服务账号类型已知，不再要求两份员工 T100 凭据。

## 6. 验收顺序与判定

先完成独立授权组件与离线契约验证，再验证真实身份和外部接口，最后接入 MetaMCP 对照。各层分别记录结果；协议仍按 [ADR-001](架构决策-001.md) 区分 `2025-06-18` 兼容组合与现代协议路径。

| 场景 | 必须取得的证据与通过条件 |
|---|---|
| 两用户本人隔离 | A、B 使用各自可信 MCP 身份；允许共用同一服务 key，但下发工号分别来自各自授权映射，返回严格对应本人，额外目标参数被拒绝。不能要求 T100 因两份不存在的员工凭据产生权限差异。 |
| BIZ 用户级拒绝 | 未授权、停用、缺映射、错误客户端/工具范围等在 BIZ 拒绝，真实业务请求计数为 0；伪造身份在认证边界拒绝。 |
| 网关启停与入口拒绝 | 无效 endpoint 凭据、停用工具/服务不能发起新的业务调用；记录实际拒绝层次。已在途调用另按撤权重验和审计规则核对，不伪报被撤回。 |
| 撤权与改绑 | 耐久登记后的前置重验失败为 0 请求；查询发生后的重验失败不输出成功，审计可定位已请求的目标及失败阶段。记录配置变更的实际生效边界。 |
| 原 API 服务级允许/拒绝 | 在获准环境使用有效服务 key 取得精确只读结果；使用错误/失效 key 获得接口服务拒绝。后者属于已发出的上游调用，不当作 BIZ 用户无权或 0 请求。 |
| 上游错误分类 | 依据接口负责人确认的 HTTP/业务码区分服务认证拒绝与其他故障；未知码保持上游错误，不能猜成员工无权或空成功。 |
| 审计与故障 | 开始记录失败为 0 请求；调用后终态登记失败不返回成功，保留待核对的开始记录。请求、调用主体、目标、阶段、结果可关联；凭据和完整员工档案不入审计。 |
| 凭据轮换与隔离 | 使用受控方式轮换或撤销服务 key，验证旧 key 不再可用及服务配置实际生效情况；故障不回退旧 key、旧环境或其他系统凭据。 |

最终签收须同时证明 BIZ 用户级授权有效、原接口服务级限制有效、两名用户本人隔离、网关组合身份可信以及调用记录可核对。不能用服务 key 连通、组件测试或原 API 服务级拒绝中的任一项替代其余项。

本次只记录决策，没有向真实 T100 发请求、迁入旧凭据或启动旧环境。新增服务账号授权实现、真实环境、网关身份与组合验证的完成状态以各自后续证据为准。

## 7. 后续系统独立决定授权模式

OA、CRM 等后续项目分别声明并验证 `per-user`、`delegated` 或 `service-account`，记录选择依据、最终授权位置及凭据范围；T100 的事实不能推广为所有系统都使用管理员 key。各项目维护自己的配置、凭据、数据、环境、工具契约和制品，通过 GOV 在 MetaMCP 聚合；不为此建立通用授权平台，也不把 T100 特有规则移入 CORE。是否共进程部署按信任域、凭据和风险评估，不改变项目与契约的独立性。
