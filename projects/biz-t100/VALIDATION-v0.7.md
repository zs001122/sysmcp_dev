# BIZ-T100 v0.7.0 验证记录

日期：2026-09-30。结论：启用/禁用的代码与契约闭环已完成，真实状态更新仍未通过。当前为 `biz-validated`；`business-validated`、`published` 均未通过。

## 业务边界与实现

用户确认员工档案是查询、资料更新和用户资料新增/修改的前提；员工资料更新只传 `employee_no/status` 时，其他省略字段保持。启停据此使用 `employee-status-v1`：批准员工存在性前查 → `employee.data.update` 最小更新 → 精确查询状态，分别固定 Y/N。没有增加建档、全量资料回写或角色/站点操作。旧用户账号启停路径在真实配置中已关闭；密码重置继续使用原用户账号接口。

每个状态工具有独立 scope，目标来自受控企业/员工/账号映射。原生验签后才授权并读取服务 key；前查后再次检查授权、绑定、调用者及令牌期限。写响应要求总 code 成功且恰好一条逐条结果，两个主键都精确匹配且无逐条错误；最终回读必须唯一、工号相同、status 等于目标。专用 `EmployeeStatusReceipt` 防止普通 ACK 被判成回读成功。只有终态审计和私有执行证据均成功，CLI 才返回 `business_verified`。

新 `enable_account` 与禁用、重置共享 SYA1 v2 操作库。显式 `prepare()` 严格识别 v1 并在原库事务内升级，保留历史、UUID 去重和跨动作未决占用；错误企业或未知模式拒绝。旧 UUID 不能换目标、动作或 Profile 重放。未决结果不自动重试或解锁。

## 真实执行结果

以下证据均使用用户已批准的既有企业、员工及显式登录账号绑定，身份为本地临时签名身份；真实个人身份未验证。企业、工号、账号、操作 UUID 和完整私有路径只留 `.runtime`。

| 实测阶段 | 实际请求 | 结果与判定 |
|---|---|---|
| 旧禁用 ACK 的独立核对 | 资料查询 | 工号唯一精确匹配，状态 Y；与禁用目标 N 不符，不能将旧 ACK 当作生效 |
| 新状态禁用 | 前查 1 次、更新 1 次 | 前查成功；更新返回 `upstream_rejected`，未取得合格成功回执，未进入成功后回读 |

| 失败后的独立观察 | 另行只读查询 1 次 | 工号精确匹配，当前仍为 Y；只记录观察，不把它用作自动解锁或重发依据 |

本轮新更新只有一次写请求，没有重试、自动启用、重复建档或全量资料回填。新操作的开始、派发与未知终态均有审计；`.runtime/live-write/status-results/` 保存实际读写阶段、预期状态和失败证据，独立只读观察关联原操作。旧 v1 库升级后校验为 v2，原 4 条操作及全部既有事件逐行不变，当前共 5 条操作、1 条未决，完整性检查通过；私有迁移前备份保留。

具体 HTTP 状态和上游原始业务码在此次失败时尚未保留，当前只能确认固定错误 `upstream_rejected`，不能推测为缺字段、权限不足或错误接口。之后已补 `write_diagnostics`：只在私有执行证据保留 HTTP 状态、受限数字执行码/SQL 码及固定类型标签，不保留描述、响应原文或凭据；没有重放本次写入来补取诊断，也不伪造历史码。

## 当前缺口与后续

接口维护方需要按私有操作时间、企业、目标及服务名核对此次 `employee.data.update` 最小状态请求的拒绝原因和实际执行情况。原始响应缺口须通过维护端记录补足；不能靠换 UUID、修改 Profile 或新建操作库绕过未决锁。确认处理结论前，同一目标的启用、禁用与重置保持阻塞。

正式 IdP、两名真实员工本人隔离、未授权零请求、有效/无效服务 key 行为、密码重置效果与交付、MetaMCP 登记及两跳仍分别待验。账号状态验证成功本身也不等于上述整体通过。
