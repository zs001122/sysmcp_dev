# REUSE-01：旧模块优先评估、合格后复用

生效日期：2026-09-29。依据：用户明确要求对 `/data/projects/mcp_auth_demo` 的已有模块优先考虑复用，但复用前必须充分评估，禁止随意直接复制。

适用范围：旧项目及用户指定的相关来源（包括 `/data/projects/account_mt_v2`）的代码、模型、工具定义、配置模板、SQL/迁移、脚本、测试、接口样例和设计成果。承接工作空间为 `/data/projects/sysmcp_dev`。本准则同时约束人工开发和自动化代理。

## 1. 原则的准确含义

**优先检查已有成果，按当前需求和证据决定是否复用；只有经过评估并满足接入条件的具体能力，才能进入新项目。**

“优先复用”要求在准备实现某项当前能力时，先检查旧仓是否已有适用资产，避免无理由重复开发。它不要求保留旧架构、追求复用率，或为了利用旧代码扩大阶段范围。FastMCP/MetaMCP原生能力、旧资产复用、最小新实现应放在同一问题下比较，选择满足要求且总体成本合理的方案。

“充分评估”要求核对实现、依赖、调用上下文、输入输出和失败路径，取得与风险相称的证据；仅看文件名、README、代码量、历史测试数量或一次正常调用不合格。范围是本次候选及其实际依赖和受影响边界，不要求为每个小函数重新审查全仓，也不新建通用审核平台。

“禁止直接复制”禁止未经评估把旧代码、目录或环境搬入新项目。完成评估后，可以按记录进行受控提取或封装；原字节复用也必须有来源、范围、适用证据和维护归属，并非免评估通道。

## 2. 评估标准

每个候选须按下表给出“满足／不满足／待验证／不适用”及证据。“不适用”必须说明原因；关键项待验证时不能记为已接受。

| 维度 | 必须回答的问题 | 最少记录或证据 |
|---|---|---|
| 当前需求 | 解决哪项当前交付问题？是否比框架原生能力或最小新实现更合适？ | 当前任务、场景、替代方案；暂时不用则暂缓 |
| 来源与成熟度 | 源commit、路径、对象是什么？是正式代码、候选补丁、未测草稿还是替身？ | 不可变源码定位、必要文件摘要、已知问题；按实际记录版权/许可证及第三方来源 |
| 职责边界 | 能否成为目标模块的一项清晰能力？是否混入其他业务、环境许可或一次性恢复？ | 候选范围和明确排除范围、目标项目、维护责任 |
| 契约匹配 | 输入、输出、错误、版本、身份、状态及副作用与当前调用方一致吗？ | 旧→新接口对照和不兼容项；不能丢字段假装兼容 |
| 依赖闭包 | 直接和间接依赖是否已声明？是否依赖旧源码、tests/scripts、全局配置或外部现场？ | import、动态加载、文件/网络/DB依赖清单及最小安装条件 |
| 框架与运行兼容 | 能否在目标Python/FastMCP、异步模型及当前协议Profile下工作？ | 当前锁定版本、构建/接口验证；取消、超时和资源释放检查 |
| 身份与权限 | 会否把用户名/参数当权威身份，回退共享账号、透传错误受众凭据或代替原系统授权？ | 信任边界及相关负例；涉及的拒绝路径须可观测 |
| 数据与持久语义 | 是否含敏感数据/凭据？状态与审计是否要求原子性？失败/未知/重试语义是否改变？ | 字段、事务、幂等/防重放和未知结果的适用范围 |
| 独立可验证性 | 能否脱离旧仓和旧环境构建、导入、测试？是否覆盖新交界？ | 隔离测试及公开接口证据；按需覆盖组件、网关和真实业务层 |
| 总体成本与维护 | 提取、适配、验证、升级和维护成本是否合理？谁维护？ | 与最小重写/原生替代的比较、回退方案；有依据估算，不编造工时 |

涉及当前外部产品能力或升级兼容性时，应核对固定版本源码、官方文档或实测，不套用旧版结论。仅复核本地纯逻辑不强制额外联网。

## 3. 可复用的必要条件

进入正式模块实现范围前，必须满足：

1. 有当前明确需求和唯一目标项目，没有因旧资产存在而新增非必要设施。
2. 来源、最小提取范围、依赖闭包和维护归属已记录；所需来源授权/许可证义务可满足。
3. 对外契约与当前要求一致，或适配方案已实现并验证；重要身份、版本、状态和错误语义没有被截断。
4. 关键安全/正确性问题已解决；没有隐式权限放宽、错误凭据回退、未知结果自动重放或敏感材料迁入。
5. 不依赖旧工作区实时路径或旧环境；新项目独立构建、相关正负例及接口测试通过。
6. 已记录复用决策、实际改动、测试范围、未覆盖项及禁用/替换办法；证据对应当前代码和依赖版本。

这些条件允许代码作为合格模块进入新仓，**不自动允许接入真实业务**。公开运行、网关组合和真实业务验收仍须分别满足当前阶段条件。历史运行许可不随代码迁移。

任一关键条件未满足，结论只能是“适配后复用，条件未关闭”“仅参考”“暂缓”或“不复用”，不得以其他项得分抵消。普通格式或兼容问题可在同一工作包修复，不需要反复请求用户审批。

## 4. 允许的复用方式与结论

| 决策 | 适用情形 | 允许的下一动作 |
|---|---|---|
| 原样封装复用 | 行为、接口、依赖符合当前要求，独立验证通过 | 按明确清单打包/纳入目标模块，保留来源；不引用旧目录 |
| 提取或适配后复用 | 核心逻辑有价值，但框架绑定、接口或现场依赖不符 | 先在隔离候选范围适配和验证；条件关闭后才接入正式路径 |
| 仅参考设计/测试 | 规则、边界样例或失败案例有价值，代码实现不适用 | 映射为当前设计/测试，注明语义差异；不搬入旧运行实现 |
| 暂缓 | 有价值但当前不需要，或关键输入缺失 | 留下理由和触发条件，不创建对应空模块或扩建设施 |
| 不复用 | 原生能力更合适，或实现不匹配、提取成本/风险过高 | 记录理由及替代方式，按当前任务最小实现 |

优先使用可独立版本化的制品和公开接口；小范围逻辑可归入唯一目标项目，不为每个函数另建包。若评估证明完整小包就是最小独立复用单元，可按记录的精确范围提取、封装和验证。同一能力不得复制到多个BIZ-ADP后各自修改。适配应纠正旧缺陷，不能为保持旧测试通过而继承不安全行为。

## 5. 明确禁止的行为

- 未评估即整仓、整目录或整模块搬迁；先把大量旧代码放进正式 `src/`，再以“以后整理”补评估。
- 仅改包名、路径、配置变量或注释就称完成重构/适配；因旧测试通过便跳过消费者契约验证。
- 通过符号链接、绝对路径、`sys.path/PYTHONPATH`、动态执行旧脚本或挂载旧源码维持运行依赖。
- 将tests、验收夹具、历史修复脚本或候选补丁直接装成产品实现；其中可分离能力也必须重新评估。
- 复制 `.env`、Token、密码、私钥、真实业务数据或外置运行目录；重新使用旧数据库、容器、证书、运行许可及现场标识。
- 原样移入绑定旧现场的迁移/恢复脚本，或因其位于“测试”目录就执行。SQL、迁移和配置模板同样适用本准则。
- 把旧模拟ERP/OA/CRM、系统Token加operator参数、离线替身或管理事务验收当作真实业务权限/委托闭环证据。
- 为迁就旧实现降低当前授权、审计、状态或协议验收要求，隐式回退配置，或恢复已封存的完整设施路线。
- 修改旧封存源码、失败记录及历史验收结论以适配新结果；覆盖旧证据或把未执行项改成通过。

允许在完成只读初筛并记录精确范围后，为验证候选将必要代码抽取到当前工作空间的隔离评估目录。该目录不得参与正式打包、运行装配或真实数据访问，不能借“实验”名义跳过评估或超出必要范围整包复制。验证通过后按实际差异迁入目标项目；失败则保留去敏评估结论并停止该候选，旧仓保持只读。

## 6. 执行流程与验证深度

流程固定为：**当前需求 → 旧资产初筛 → 最小候选与依赖评估 → 决策和条件 → 隔离适配/验证 → 有范围的接入 → 集成验收**。

| 候选类型 | 必需的验证深度 |
|---|---|
| 纯模型/无I/O规则 | 相关正常、边界、错误输入及旧→新契约对照；独立安装/导入；无隐藏副作用 |
| 框架绑定/业务连接器 | 上述检查＋目标FastMCP/HTTP契约、错误映射、超时取消、资源释放及凭据隔离 |
| 身份/权限/持久状态/迁移 | 上述适用项＋权限负例、并发/事务/提交未知/重启等受影响保证；真实运行仍须明确环境与授权 |
| 测试/设计资料 | 核对断言是否匹配当前事实和Profile，替身是否掩盖新交界；保留来源和不适用项 |

测试只覆盖实际承诺的行为；不要求纯函数补数据库演练，也不允许用纯函数单测替代数据库、身份或业务验收。足够的同基线证据可引用，并说明为何仍适用；环境、依赖、接口或信任边界变化的部分必须重新验证。

评估、实现和维护责任具名记录，可以是实际执行者/代理角色，不得虚构业务签收。只有任务或既有规则要求独立审核的范围才另行安排，不将本准则解释成每次提取都需用户批准。

## 7. 结合旧项目的评估重点

以下仅是初筛线索，**不是本次已接受的复用名单**：

| 旧资产 | 可评估价值 | 必须解决的边界 |
|---|---|---|
| `access_relations`模型/约束 | 精确身份、唯一性、版本与失效规则 | 当前业务确实需要；接口与完整绑定一致，不能只取旧快照丢父级版本 |
| `adapter_core`策略/义务/结果逻辑 | 已有规则与错误/结果分层 | 不整体搬旧管线；同步/异步、返回形状和当前FastMCP边界须对齐 |
| `audit_contract`和事务原语 | 事件字段、稳定命令、共事务经验 | 按阶段明确所需保证；旧管理事务不是业务执行流水 |
| `platform_storage` | 特定数据库原语可能有价值 | 拆除tests/scripts及固定环境依赖；受影响事务保证须在新环境证明 |
| 旧工具、HTTP适配、测试 | 参数Schema、API形状、负例和故障经验 | 真实API、合法业务凭据和权限边界未定时仅参考，不继承模拟业务授权与重试假设 |

初筛依据来自[旧项目架构分析](../reports/mcp_auth_demo-20260929/项目架构分析与模块化闭环规划.md)。该报告可定位候选，但不能代替本次具体提取范围的评估。

## 8. 在项目准则中如何记录

- **AGENTS.md**：保留规则编号REUSE-01、强制“先评估后复用”、准入/禁止要求及本文链接，作为日常执行入口。
- **本文**：统一维护详细标准、流程和判断口径；其他文件引用，不维护不同版本的重复规则。
- **候选记录**：具体需求出现时，按[评估模板](复用评估模板.md)创建 `docs/reuse/RU-<编号>-<能力>.md`；没有候选时不预建项目或填写虚假通过记录。
- **目标项目README/变更说明**：链接RU记录，说明实际导入的能力、公开版本、改动及限制；迁移或提交说明携带同一RU编号。
- **STATUS.md**：只列影响当前主线的候选和证据，分别记录“评估完成、适配中、模块验证通过、组合通过、真实业务通过”。
- **记录更新**：源commit、范围、依赖、接口或信任边界变化时，补可追溯修订并重评受影响项；不覆盖旧结论，不无条件复审全仓。

规则建立时未接受任何旧模块；后续具体候选与阶段证据以 RU 记录和 STATUS.md 为准。当前已评估的首个业务候选见 [RU-001](reuse/RU-001-t100本人档案.md)，仅限已记录的适配范围，不沿用旧运行许可或业务验收。
