# 模块边界与接口约束

日期：2026-09-29。适用范围：`/data/projects/sysmcp_dev` 下所有现有及新增模块。

## 1. 约束目标

模块边界固定职责、依赖方向和可验证接口，使新增模块不会通过隐式依赖改变现有行为。扩展空间保留在公开扩展点、实现替换、版本化契约和部署组合中。约束针对系统不变量，不提前锁死未来尚未验证的业务形态。

必须稳定的内容包括：职责归属、公开接口、数据与凭据所有权、默认拒绝、失败传播、版本语义和证据边界。可以演进的内容包括：内部实现、库选择、运行拓扑、容量策略、可选能力和新协议Profile；演进必须通过明确契约及兼容验证。

## 2. 模块边界

| 模块 | 负责 | 对外接口 | 最小依赖 | 禁止事项 |
|---|---|---|---|---|
| GOV / MetaMCP | 服务登记、组合、namespace、endpoint、入口访问控制、工具暴露和组合证据 | MetaMCP入口；BIZ服务发布描述；发布状态与去敏证据 | 固定MetaMCP及其数据库、目标服务网络可达 | 实现业务规则；保存上游业务凭据/员工映射；导入BIZ源码；直接改BIZ存储 |
| CORE | FastMCP服务工厂及被多个项目证明需要的通用小能力 | 版本化Python公开包与测试契约 | Python、FastMCP及明确锁定的库 | 包含系统字段、业务授权、网关对象或共享业务数据库；部署成无必要转发层 |
| BIZ-ADP项目 | 单一业务系统的工具、API适配、业务模型、授权、运行配置和业务审计 | 版本化包/制品、MCP工具契约、`service-release.md` | CORE公开包、该系统已批准API、项目自有存储 | 跨项目导入内部源码；读取其他模块存储；把业务秘密交给GOV；提供任意URL/认证头/SQL |
| FastMCP运行单元 | 承载一个或多个已经评估可共存的BIZ制品 | Streamable HTTP、健康检查和运行观测 | 已构建制品、受控配置和身份Provider | 因方便而混用凭据/信任域；共用未声明状态；一个模块故障无界影响其他模块 |
| 既有业务系统/API | 对实际执行身份做最终业务限制并返回事实 | 经负责人确认的API契约 | 原系统自身 | 由本项目假造权限或错误语义 |

## 3. 允许的依赖方向

```text
MCP Client → GOV → FastMCP运行单元/BIZ → 既有业务API
                         │
                         └── 安装 CORE 公开包
```

- GOV只依赖BIZ的网络接口和发布描述，不依赖其Python内部结构。
- BIZ只依赖CORE公开API，不反向要求CORE感知具体系统。
- 不同BIZ项目之间默认无运行时依赖；确有跨系统编排时，先建立独立编排模块和显式契约，不直接互读数据库。
- 观测、身份或配置实现可替换，但替换点必须由模块自己的公开端口定义。

## 4. 每个模块必须声明的契约

新增模块在开始实现前至少在README或专用契约文档记录：

1. 业务目的、明确不负责的范围和责任人；
2. 输入、输出、错误、超时、取消、幂等及数据分类；
3. 公开接口与内部实现的分界，含版本和弃用策略；
4. 身份、凭据、配置、持久状态和审计分别由谁持有；
5. 上下游依赖、最小运行条件、健康检查和故障隔离；
6. 扩展点及其限制，不能依赖未来未定义行为；
7. 独立验证、契约测试、受影响模块回归和发布证据；
8. 停用、回滚、迁移及残留数据处理方式。

未声明或未验证的行为按不支持处理；不能用宽泛的“兼容”“通用”承诺代替契约。

## 5. 稳定接口与扩展点

- 公共接口只包含调用方完成当前用例所需的最小集合；内部类、目录、数据库表和MetaMCP内部对象不是公共接口。
- 新增可选字段默认可缺省且不改变既有语义；调用方不认识的新枚举或错误必须有明确处理策略。
- 工具名称、输入Schema、输出字段、授权语义或副作用发生不兼容变化时，发布新契约版本或新工具名，并给出迁移与停用窗口。
- 身份Provider、业务客户端、日志/审计端口和协议Profile可作为替换点；具体实现留在所属模块，不把所有差异压成一个万能配置。
- 部署可从独立进程调整为受控组合，也可重新拆分，但MCP工具契约、数据所有权和安全边界不得因此隐式改变。

## 6. 新增模块准入

新增模块必须同时满足：

- 有已确认的当前业务用例，不创建只有目录和占位接口的空模块；
- 已执行REUSE-01评估，说明复用、适配、参考重写或不复用结论；
- 与现有模块的职责无重叠，或已记录为何拆分/替换及迁移方案；
- 可以独立构建、测试和形成制品，不靠源码路径或共享虚拟环境运行；
- 默认配置不会注册工具、启动监听、访问真实系统或改变现有namespace/endpoint；
- 公开契约与失败边界可测试，新增依赖和持久状态有明确所有者；
- 受影响模块的契约和回归测试通过，结果记录到本模块及集成证据中。

## 7. 变更影响与回归

| 变更 | 最低验证 |
|---|---|
| 仅内部实现且公共行为不变 | 本模块单元/契约测试；证明公开Schema与错误不变 |
| 新增向后兼容工具或可选能力 | 本模块测试、GOV工具白名单核对、既有工具发现/调用回归 |
| 公共契约、身份或错误语义变化 | 新版本契约、上下游兼容测试、迁移和回滚演练 |
| 凭据、信任域、写能力或持久状态变化 | 重新评估运行单元隔离、安全边界、真实权限和审计 |
| GOV组合或协议Profile变化 | 固定版本两跳测试、入口拒绝、停用、直连/网关对照及所有受影响服务回归 |

任何新增模块默认处于未发布状态。只有自己的验证通过，且GOV对其登记和组合单独通过后，才能影响目标namespace或endpoint。

## 8. 防止约束过紧

本规范不规定所有系统使用同一身份模式、同一数据库、同一错误码、同一运行进程或同一发布节奏，也不要求为未来需求预建抽象层。发现新需求时，先在所属模块通过窄接口实现；当至少两个真实模块出现稳定共性并有测试证据，再考虑抽取公共能力。

若现有边界确实阻碍已确认需求，应通过新的ADR修改边界，列出影响、兼容路径和回滚方式。不得通过跨目录导入、共享秘密、直接改库或复制内部代码绕过边界。
