# ADR-004：GOV 统一服务注册与发布

原决策日期：2026-09-29；现状补充：2026-09-30。状态：已采纳。原决策时MetaMCP产品容器已运行、T100登记与两跳尚未验收；后续0.9.1已完成本工作空间T100单服务双端点的内部登记与组合验证，正式身份及完整发布仍未签收。部署拓扑以 [ADR-009](架构决策-009-T100账号操作网关接入.md) 为本阶段最新决定，实际证据见 [GOV 部署记录](../projects/gov/部署记录.md)。容器健康不等于身份或业务验收通过。

## 1. 决定

短中期由 GOV 中的 MetaMCP 统一管理已封装 MCP 服务的登记、组合与发布。业务系统适配继续在独立 BIZ-ADP 项目中开发和验证；CORE 只提供已被多个项目证明需要的轻量公共能力。

独立项目是源码、依赖、契约、测试和制品的管理边界，不强制每个业务系统永久对应一个进程。FastMCP 运行单元按凭据、信任域、读写风险、故障隔离、容量和发布节奏划分。持有管理员服务凭据、提供写工具或处于不同信任域的模块默认独立部署；合并部署必须有明确收益、隔离方案和回归证据。

## 2. 职责归属

| 范围 | GOV | BIZ-ADP | CORE |
|---|---|---|---|
| 服务实现 | 不持有业务源码，不实现业务规则 | 实现工具、业务模型、API适配与启动入口 | 提供小型公开库和FastMCP工厂 |
| 注册与发布 | 持有服务目录、环境地址引用、协议Profile、namespace、endpoint和工具暴露 | 提交去敏发布描述 | 不感知具体网关对象 |
| 身份与授权 | 控制网关入口和服务/工具发布范围；记录身份承载要求 | 验证资源身份，执行用户/委托/服务账号模式及业务范围 | 只提供通用扩展接口，不决定业务授权 |
| 凭据 | 持有MetaMCP自身所需密钥及受控引用 | 持有上游业务凭据、映射和授权配置 | 不持有运行凭据 |
| 数据与审计 | 保存网关配置和组合证据 | 保存必要业务状态与业务调用记录 | 不建立共享业务数据库 |
| 验证结论 | 签收登记、组合、发布与两跳结果 | 签收组件、HTTP、原生MCP和真实业务结果 | 签收公共库自己的接口行为 |

GOV 不读取 BIZ 内部数据库或文件，不复制业务密钥、员工映射、允许清单、完整业务响应及业务审计。BIZ 不直接修改 MetaMCP 数据库或依赖其内部模型。双方只通过公开 MCP/HTTP 契约、发布描述、受控配置引用和去敏证据交互。

## 3. BIZ 与 GOV 的接口契约

每个待接入服务在所属 BIZ 项目维护 `docs/service-release.md`。它至少包含：

- 稳定服务逻辑 ID、系统、用途、负责人和运行单元边界；
- 制品名称、不可变版本或摘要、启动方式及回滚版本；
- 每环境的地址引用和网络前提；仓库不记录真实密钥，敏感地址按环境受控管理；
- Streamable HTTP 路径、协议 Profile、初始化要求、超时、健康检查和容量边界；
- 允许暴露的工具、工具契约版本、读写属性和 Schema 摘要；
- 资源身份、原客户端归因及业务执行模式要求；
- BIZ 验证证据、已知限制、失败语义、停用和回滚方式。

GOV 接收发布描述后，返回或记录服务登记 ID、namespace/endpoint 映射、实际组合版本、工具暴露结果、验证状态、错误与回滚记录。具体接入步骤见 [GOV 服务接入规范](../projects/gov/docs/service-onboarding.md)。

## 4. 三类凭据不可混用

1. **MetaMCP 入口或管理凭据**：只用于访问或管理 GOV。
2. **BIZ 资源身份上下文**：让业务服务可信识别调用主体、客户端和目标资源；不能由任意Header或工具参数自行声明。
3. **上游业务凭据**：由BIZ按已声明的 `per-user`、`delegated` 或 `service-account` 模式取得和使用。

任一层的凭据成功都不能替代其他层验证。尤其 MetaMCP API Key 不能当成员工身份，T100服务管理员key也不能授予MCP用户管理员能力。

## 5. 状态与证据

服务发布主状态按以下顺序推进：

`candidate → biz-validated → gov-registered → composed → published`

- `candidate`：候选及边界已明确，不表示可运行。
- `biz-validated`：BIZ独立制品和声明的组件证据通过。
- `gov-registered`：GOV已登记实际制品、地址引用和协议配置。
- `composed`：已进入目标namespace，工具白名单与发现结果已核对。
- `published`：private endpoint已发布，入口拒绝、调用、停用和直连/两跳对照通过。

上述发布判定还以已声明的身份承载契约满足为前提。当前T100临时共享连接只取得内部登记／组合证据，不能因private endpoint存在、工具发现或入口Key通过就签收正式 `published`；具体缺口与后续状态见本页第7节及ADR-009。

`business-validated` 是独立证据维度，表示获准真实环境中的业务权限与审计通过；不能由 `published` 推断。服务还可进入 `disabled` 或 `retired`，必须保留原因、生效时间和影响范围。

## 6. 接入与变更流程

1. BIZ完成独立构建、契约测试、原生MCP验证和必要的复用评估。
2. BIZ提交去敏服务发布描述；GOV核对字段、证据、工具命名、身份要求和风险边界。
3. GOV使用目标环境的受控地址引用登记服务，记录实际MetaMCP版本和协议协商结果。
4. GOV先加入限定namespace，再创建或更新private endpoint；默认最小工具白名单。
5. 联调依次验证发现、调用、错误入口Key、身份替换、服务/工具停用、超时和直连/两跳结果。
6. 真实业务验证按系统声明的执行模式单独签收；失败时定位到入口、组合、BIZ或上游层。
7. 变更先更新发布描述和影响分析，再在受限范围验证；回归通过后扩大范围，失败按记录的版本回滚。

MetaMCP的实际配置载体以固定版本支持的UI、API或持久化方式为准。本仓库保存去敏期望状态、操作步骤、对象ID和证据；在未验证上游支持前，不假定存在声明式导入能力，也不直接修改产品内部数据库。

## 7. T100 首个落点与后续状态

### 原决策时点：2026-09-29

以下两段保留原候选范围及当时缺口；其中工具、尚未登记等表述已由后续四接口和ADR-009阶段替代，不再限制当前已获授权的维护能力。

`biz-t100` 是首个候选服务，当前允许登记的业务能力仍只有 `get_my_t100_employee_record`。其管理员服务key、员工映射、允许清单、授权策略和SQLite查询记录全部留在BIZ-T100；GOV只登记服务制品、地址引用、协议、工具白名单和组合状态。

当前 T100 尚缺实际服务地址、正式资源身份装配及服务侧凭据装配证据，也未取得 MetaMCP 登记与组合证据；已有网关产品容器不能补足这些条件，因此不得创建假登记或将 T100 状态提升为 `gov-registered`。先由BIZ-T100补齐 `docs/service-release.md` 的实际字段，再进入GOV流程。

### 后续状态：2026-09-30，BIZ-T100 0.9.1

员工新建、查询、更新及账号维护四工具已在同一个FastMCP实例实现。GOV登记 `sysmcp-t100` 一个T100 MCP server，查询／账号两个namespace及private endpoint各开放对应工具；该数量仅指本工作空间管理的T100对象。工具范围仍受签名scope、BIZ主体及目标许可约束，不因同进程实现而全部发布。

当前 `gov-registered`／`composed` 有证据，临时共享连接不透传真实外部用户身份，用户级入口Key也不代替员工授权。`business-validated` 与完整 `published` 仍未签收。管理员凭据、员工／账号范围和审计继续归BIZ，稳定责任边界不变；当前对象与历史替代关系见 [GOV项目梳理](../projects/gov/docs/project-overview.md)。

## 8. 扩展原则

新增业务系统沿用相同发布接口，但各自声明身份模式、错误、时限、数据和审计边界。只有多个已运行模块出现相同且稳定的需求，才提取到CORE；只有MetaMCP出现经验证的治理缺口，才评估扩展GOV或迁移产品。通用边界、兼容性与新增模块准入见 [模块边界与接口约束](模块边界与接口约束.md)。
