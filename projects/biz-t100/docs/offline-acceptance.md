## 1. 离线验收的目标

在不依赖真实 IdP、业务服务器或网关的情况下，验证“签名调用身份 → 受控本人授权 → 实际 T100 请求 → 严格响应 → 耐久审计”完整组件链。真实个人身份来源尚未提供，不妨碍完成 `biz-validated`；不为测试增加产品中的固定用户、假认证默认值或新的 IAM 平台。

测试通过原生 FastMCP HTTP 路径调用产品工具，使用测试期间动态生成的签名密钥和 Token、临时受控策略、动态合成 service key、实际 `FileServiceAccountAccess`、T100 客户端和临时 SQLite。上游使用能捕获真实 `httpx.Request` 的隔离传输替身，不连接任何真实接口。仅返回预设 `EmployeeRecord` 的假 Reader 不能独自证明整条链符合本契约。

签名私钥、Token、service key 及员工数据只存在测试内存或临时私有文件，不进入产品 wheel、源码示例、GOV 配置或日志。新用例不以真实身份和凭据为输入；既有固定合成字符串也不能被装配为默认运行身份或凭据。

## 2. 唯一员工来源与企业边界

一般接入允许两种明示来源：经授权身份方签发并验证的权威员工号 claim，或受控 `issuer+subject → employee_no` 映射。必须选定来源及其责任方，不能因为一段内容已签名就让其自动获得员工号决定权。

**当前 T100 仅采用受控映射。** 普通 Header、姓名、邮箱、MetaMCP Key 和工具参数不能选择员工；Token 中未被选为权威来源的已签 `employee_no` 也必须被忽略。若后续改用权威员工 claim，须另改契约和实现并增加验收，不能把当前映射测试宣称为该路径通过。

固定测试身份 A、B 分别映射 E001、E002；以不同主体或不同 issuer 区分身份，禁止仅用姓名或邮箱匹配。同一 `issuer+subject` 多条映射使策略整体无效，不能任选一条。

每次捕获请求必须同时断言：

- `datakey.EntId == 当前服务受控配置的 enterprise_id`；
- `payload.std_data.parameter.employee_no == 此次许可得到的 employee_no`；
- 目标为固定员工只读服务，key 是服务侧合成 key，不是入口 Token、网关 Key 或用户参数；
- 响应的员工列表恰好一条，员工号与授权对象完全相等；不接受零条、多条、模糊匹配或其他员工，不查询全量后过滤。

判断对象使用 `(enterprise_id, employee_no)`，不能仅因两个环境员工号相同就合并身份或审计。增加同员工号、不同企业配置的隔离对照；姓名只作展示。当前响应未提供可独立验证的企业字段时，企业证据来自受控目标配置、捕获请求和固定企业审计，不补造上游事实。

## 3. 请求计数与审计语义

下表中的请求数是**模拟上游实际收到的业务 HTTP 请求数**，不包含 MCP 初始化、工具发现、健康检查或客户端方法被调用次数。每例清空计数，默认不重试；并发用例通过同步屏障制造真实重叠，不能顺序调用后称为并发。

审计以同一 `request_id` 关联可信 `issuer`、`subject`、`client_id`、目标员工、服务固定 `enterprise_id`、`tool_name` 和结果。企业及工具由 runtime/服务契约固定，不接收用户参数。终态新增 `upstream_attempted`：只表示已进入 `EmployeeReader` 调用，不保证请求已经送达、上游完成或返回。必须将它与独立捕获的 HTTP 计数对照，不能相互替代。

本人查询审计 schema v2 用于上述事实；不兼容旧库须拒绝写入，不通过偷偷改库或丢历史记录来让测试成功。四接口维护使用独立 SYF1 库，当前已有真实上游调用与手测反馈，不据此改动本人查询历史库。终态写失败时保留 `query_started` 供调查；没有终态就不能从缺失字段推断“未派发”。

初始认证失败、参数拒绝没有可信业务调用，不能编造员工审计。已取得可信调用者但授权失败时，允许只有 `query_failed`，目标员工为空，`upstream_attempted=false`，不能伪造 `query_started` 或成功。策略初始拒绝还须证明 key 内容读取次数为 0；健康元数据访问不算 key 内容读取。已先合法授权、后发生撤权的场景不要求把先前合法读取计为 0。

## 4. 必须覆盖的离线矩阵

以下均为待逐项执行、记录的断言，不代表本文已经运行这些测试。

| 场景 | 必须返回或拒绝 | 上游请求数 | 审计与附加断言 |
|---|---|---:|---|
| A 映射 E001 | 仅返回 E001 白名单档案 | 1 | start → success；A、固定企业、E001、工具及 request_id 一致，终态 attempted=true |
| B 映射 E002 | 仅返回 E002 白名单档案 | 1 | start → success；B、固定企业、E002 一致，不能串为 A，attempted=true |
| A/B 并发 | 各自只返回本人 | 各 1 | 两个独立 request_id，各自身份、企业、员工和终态匹配，无串数据 |
| 同工号、不同企业配置 | 请求和结果限定各自配置中的企业对象 | 每次 1 | 捕获企业/工号对及审计企业各自一致，不能只比较工号 |
| 未映射用户 | 拒绝，不返回员工数据 | 0 | 初始授权失败，attempted=false；key 内容读取 0 |
| 已停用用户 | 拒绝，不返回员工数据 | 0 | 初始授权失败，attempted=false；key 内容读取 0 |
| 错误客户端 | 在身份或策略层拒绝 | 0 | 按实际拒绝层记录，无成功；若已有可信主体则失败终态 attempted=false；key 内容读取 0 |
| 缺工具许可或所需 scope | 在对应身份/授权层拒绝 | 0 | 不默认授予工具；无成功，key 内容读取 0；不能将 scope 缺失解释为业务已调用 |
| 缺失、过期、伪造 Token | 认证失败 | 0 | 无伪造业务身份或员工审计，无 key 内容读取 |
| 工具参数传其他员工号 | 参数校验失败 | 0 | 不回显注入值，不进入本人查询，无业务成功或 key 内容读取 |
| 同身份映射多个员工 | 配置无效，拒绝 | 0 | 不取第一条；已有可信主体时失败终态 attempted=false；key 内容读取 0 |
| 普通 Header、姓名、邮箱、MetaMCP Key 或已签 employee_no 试图覆盖 A 的映射 | 有效 A 身份仍只查 E001；仅凭上述输入不能认证 | 有效 A 为 1；无有效身份为 0 | 捕获请求仍为受控企业/E001；不能出现伪造目标或伪造主体 |
| 上游返回不同员工号 | `upstream_employee_mismatch`，不返回员工数据 | 1 | start → failed，attempted=true；审计保留获准目标，不把错目标写成成功 |
| 上游返回零条员工 | `employee_not_found` | 1 | start → failed，attempted=true；不当空成功 |
| 上游返回多条员工 | `employee_not_unique` | 1 | start → failed，attempted=true；不从多条中筛选本人 |
| 管理员 service key 失效 | 模拟上游 HTTP 401，对应 `upstream_unauthenticated` | 1 | start → failed，attempted=true；不记为 BIZ 前置拒绝，不回退其他 key |
| 耐久开始后、业务调用前撤权或改绑 | 重验拒绝，无员工数据 | 0 | start → failed，attempted=false；保留原请求关联和拒绝阶段，不静默改查新员工 |
| 上游返回后撤权 | 不返回员工数据 | 1 | start → failed，attempted=true；结合捕获请求证明已调用，不能报未执行 |
| 审计开始记录失败 | 拒绝，无员工数据 | 0 | 不出现成功，attempted=false；不能声称已有耐久 start；存储可用时才记录失败事实 |
| 审计终态记录失败 | 不返回成功 | 1 | 已有 start；所有终态均无法持久化时保持 pending，不推断未派发或自动重放 |
| 超时 | 固定、去敏的超时错误，不自动重复调用 | ≤1 | attempted 按是否进入 Reader 如实记录；已派发的请求不得报成前置拒绝，终态无法提交时保留 pending |

每个实际请求都须满足上一节的企业/员工号精确断言，而不仅验证返回内容。拒绝、异常、CLI 输出和审计还须检查没有合成 Token、service key、完整员工响应或配置内容泄漏。

## 6. 三种状态分别签收

| 状态 | 判定范围 |
|---|---|
| `biz-validated` | 独立制品与声明的离线矩阵通过；不需要真实个人身份源或业务服务器，不代表真实权限或发布 |
| `business-validated` | 真实可信个人身份、权威员工号或唯一映射、原 API/BIZ 分层权限及审计通过 |
| `published` | GOV 实际登记、工具白名单、private endpoint、入口拒绝/启停及两跳契约通过 |

后两者为独立证据维度，不能互相推导。当前缺真实身份或上游验收时继续离线开发；不创建假登记、不提高真实状态，也不因 GOV 容器已运行就声称服务已发布。

## 7. 后续真实集成的独立矩阵

真实环境可用后，按 [服务账号决策](../../../docs/架构决策-003-T100服务账号授权.md) 与 [GOV 接入规范](../../gov/docs/service-onboarding.md) 单独执行；以下不是离线准入条件。

| 项目 | 必须取得的真实证据 |
|---|---|
| 身份到员工 | 可信真实个人身份能取得已选定的权威员工号，或经唯一受控映射得到员工号；T100 当前采用映射 |
| 两名员工 | 两名真实用户各查本人，企业/员工号及返回档案一致；service key 相同不能使本人范围合并 |
| 未获准或停用用户 | 至少一个真实对象在前置层被拒绝，业务请求数为 0 |
| service key 合约 | 有效 key 的合法查询与失效 key 的原 API 拒绝均有证据；历史错 key 问题不能由模拟 401 关闭 |
| 直连与网关 | 同一可信身份的直连/MetaMCP结果、错误及对象范围一致，原客户端归因可核对 |
| GOV 拒绝与停用 | 错误入口 key、服务停用、工具停用分别使该请求触发的 BIZ 业务请求数为 0；不混入发现/健康探测或已在途请求 |
| 审计关联 | 外部可信身份 → 固定企业和员工号 → 工具 → request_id → 结果可核对；派发、响应、终态缺失分别如实解释 |
