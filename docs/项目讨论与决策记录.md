## 统一维护整条链路的入口

编号：DEC-001。来源：用户在2026-09-30提出“最终还是要有一个表或者工具做整个链路的维护，不然每个地方都要去调整修改”，并要求记录。当前已记录需求，统一维护工具尚未实现。

### 问题与结论

身份、员工与账号绑定、业务授权、服务登记及工具开放分属不同位置。保留这些责任边界的同时，需要集中维护操作，避免每次新增用户、改绑或撤权都分别编辑多个配置。

统一维护入口接受一次变更提交，通过各层公开管理接口或经验证的受控配置发布方式完成下发，再逐项核验。操作者应看到各环节的当前状态、生效版本和关联审计；部分失败必须明确显示未完成环节。

可以有链路总览表或维护工具。具体载体尚待选择，总览记录对象关联、受控引用、版本与核验状态；业务数据的权威归属保持不变。

### 职责与数据归属

| 位置 | 权威数据与责任 | 统一维护入口如何协作 |
|---|---|---|
| 身份源 | 可信用户标识、用户启用及停用状态 | 引用并调用获准的身份管理能力，不自建第二份用户身份库 |
| BIZ项目 | 员工与账号映射、动作及目标范围许可、上游凭据、业务审计 | 经该项目公开管理契约或受控配置发布维护，不由GOV直接读写业务存储 |
| GOV及MetaMCP | 服务、namespace、endpoint、工具发布与入口访问控制 | 使用受支持管理能力调整并核验，不直接修改产品内部数据库 |
| 统一维护入口 | 变更提交、链路总览、下发协调、结果核验及变更审计 | 使用受控引用关联各层结果，不复制业务规则、上游密钥或签名私钥进GOV |

本人服务通过可信身份映射确定本人员工；操作员维护通过可信主体的动作和目标许可判断可操作范围。业务目标工号不能作为调用者身份。员工号和登录账号分别维护，不能默认相等；网关Key、调用者身份凭据和T100服务凭据分别使用。

以上边界沿用 [T100服务账号授权](架构决策-003-T100服务账号授权.md)、[GOV统一注册与发布](架构决策-004-GOV统一服务注册与发布.md) 和 [模块边界与接口约束](模块边界与接口约束.md)。当前T100部署与网关边界见 [ADR-009](架构决策-009-T100账号操作网关接入.md)。

### 开发目标与验收要求

统一维护工具的最小能力为查看、变更、下发、核验、审计。优先覆盖用户新增与停用、员工及账号绑定、业务授权调整、服务及工具启停；首批实际支持范围在实现前明确，不将所有功能一次性预建。

| 验收事项 | 可验证要求 |
|---|---|
| 集中维护 | 对一个已支持场景，操作者只在统一入口提交一次，无需再逐处手工编辑 |
| 分层下发 | 每个受影响模块可追溯到本次变更；未涉及的目标与权限保持不变 |
| 生效核验 | 各环节分别展示成功、失败或未完成及生效版本；配置已保存不等于执行已生效 |
| 部分失败 | 任一环节失败时不报告整体成功；给出失败位置和已有完成事实，不擅自重放业务写入 |
| 审计关联 | 可由同一变更编号核对操作者、变更范围、各层处理和核验结果，敏感内容按所属模块留存 |
| 数据边界 | 不形成另一份需要人工同步的业务映射或许可，不把业务秘密复制进GOV |

实际实现优先复用已有身份源、MetaMCP和BIZ能力；按 REUSE-01 评估后接入。此项是轻量运维能力的目标，不改变当前两类日常业务测试入口和独立项目原则。

### 待讨论事项

下列问题尚未决定，不作为已采纳的设计：

| 问题 | 需要形成的结论 |
|---|---|
| 首批维护场景 | 先支持哪种变更，其受影响模块、验收用例和目标范围 |
| 工具形态及归属 | 使用已有管理界面、轻量命令工具或页面；由哪个独立边界维护 |

## DEC-002：BIZ-T100 交付收尾与写入幂等边界

日期：2026-10-08。来源：2026-09-30 开发齐备性审计及用户随后要求“继续”。本轮收尾范围已确认；跨请求业务幂等的具体方案仍待讨论，不能据需求记录宣称已实现。

### 本轮决定与边界

交付新补丁候选 0.9.2：修正兼容查询工具中员工 status 的错误解释，将 live.py 本机签名主体固定为 temporary-local-operator，密钥和令牌仍逐次生成并原生验签，原有动作与批准目标许可不变。同步当前说明、状态和版本登记，沉淀唯一开发待办矩阵、验证、制品及去敏源码基线准备；不增加日常业务脚本。

现有部署基线仍为 0.9.1。本轮不改运行配置或 schema、不部署或启停服务、不续签或更新网关令牌、不调用真实 T100、不自动提交或推送。旧制品、DOCX、审计、未决操作及历史验证原样保留，不将候选提升为 business-validated 或完整 published。

### 编号防重与业务幂等

现有请求编号防重、unknown 目标占用和禁止自动重试已实现，但不同请求编号的相同成功业务报文仍可能再次派发。它们不能替代业务幂等键，也不能证明正式写发布的幂等验收通过。已获用户授权的限定内部真实测试作为阶段例外保留，正式发布继续遵守 [BIZ-ADP 规范第 6 节](BIZ-ADP开发规范.md#6-写入单独验证与发布)。

下列方案事项尚未决定，不进入当前运行路径：

| 待讨论事项 | 必须形成的公开结论 |
|---|---|
| 上游能力与效果核对 | 哪些写动作支持上游去重、状态／操作结果查询；无证据时不猜测成功或安全重试 |
| 键作用域 | 主体、客户端、企业、动作、员工／账号目标与键的关系；生命周期与撤权后的处理 |
| 同键输入 | 请求意图与最终报文如何比较；同键不同输入明确冲突，不能静默覆盖 |
| 并发与未知 | 并发同键最多一次派发；超时、审计失败及响应丢失仍保持待核查，不自动重试或解锁 |
| 存储兼容 | 公开数据版本、旧库迁移、历史记录保留、安装升级及回滚验证；不擅自改现有 SYF1 运行库 |
