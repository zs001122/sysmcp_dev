## 当前内部连接不能替代的身份能力

MetaMCP 2.4.22 不透传外部调用者 JWT。两个端点共用一个受控内部连接主体，BIZ 看到的是该连接主体而非访问网关的真实员工。其临时 JWT 仅查询＋账号维护两个 scope，最长一小时；BIZ 再限制批准员工／账号配对和 `status-password` 报文。续签和管理 API 更新是已实现的运行流程，自动跨层维护工具尚未实现。

两个端点各配置访问 Key，但当前 MetaMCP Key 是用户级凭据，不天然绑定某一 endpoint。工具白名单能选择查询或账号工具，不能证明同一 Key 在其它端点不可用，也不能替代 BIZ 的员工和账号范围授权。正式集成必须明确身份承载及客户端归因契约，不能仅增加 Key 或透传一个普通 Header 就声称已取得可信个人身份。

675 项是 0.9.1 接入时的相关离线回归；该次实际 T100 读写均为 0。0.9.2 的本轮证据见 [候选验证](../VALIDATION-v0.9.2.md)，不继承历史测试数量。此前真实查询及账号回执分别保留在对应历史验证中。已有连接不要求重复登记，已有 ACK 不证明账号效果；证据索引见 [0.9.1 验证](../VALIDATION-v0.9.1.md)、[0.9.0 历史验证](../VALIDATION-v0.9.0.md) 和 [收敛验证](../VALIDATION-consolidation-20260930.md)。

## 正式验收顺序

1. 固定真实IdP验签和员工唯一映射，确认本地临时身份不能进入正式入口。
2. 两名获准员工分别取得本人资料；未授权或停用用户前置拒绝，T100请求数为0。
3. 验证管理员凭据有效、失效和业务拒绝行为，核对审计及撤权路径。
4. 核对登录账号启停及密码重置的实际效果，并关联可信操作者、独立员工／账号目标、请求和审计；员工档案查询不作账号效果证据。
5. 在既有单服务、两端点结构上核对正式环境与身份契约；若出现不同凭据或信任域，再按验证后的需求调整部署。
6. 验证同一可信用户的直连／两跳结果与归因、白名单、private endpoint、错误 Key 及停用零业务请求，补齐正式 GOV 验收。

| 状态 | 当前结论及签收要求 |
|---|---|
| `biz-validated` | 既有声明范围有离线代码与契约证据；0.9.2 另按本轮实测签收，不等于真实员工验收 |
| `business-validated` | 尚未签收；真实可信身份、唯一员工来源、真实上游与分层权限／审计分别取得证据 |
| `published` | 当前仅内部 `gov-registered`／`composed`；真实身份链及正式 GOV 组合验收缺口未关闭 |

每一步只更新对应证据状态；`business-validated` 和 `published` 是独立维度，不能互相推导，不能用临时合成身份填补真实用户验收。

具体缺项及优先级只维护在 [开发清单](development-checklist.md)；本页只定义集成输入与判定边界。0.9.2 交付收尾不实现正式身份、跨请求幂等或统一维护工具，不改变部署、运行许可或业务数据。原输入来源和只读阶段限制见 [历史快照](history/20260930/integration-inputs.md)。
